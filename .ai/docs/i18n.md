# i18n — User-Facing Text Rules

Applies when editing `.vue` / composables that render user-visible strings.

## Setup (ground truth)

- Lib: `vue-i18n` v10 (composition API, `useI18n()`).
- Setup file: `.vitepress/theme/i18n.ts` (created via `setupI18n()` in `enhanceApp`).
- Locales: `locales/{vi,en}.json`.
- Default locale: `vi`. Fallback: `vi`. (English-only browser users still see Vietnamese for any missing keys.)
- Locale auto-detected on first boot (`navigator.language`), persisted to `Settings.locale`, user-switchable in Settings drawer.

## Rule

All user-facing text MUST go through `t('key')` (`useI18n()` in `<script setup>`) or `$t('key')` (template). Both locale files updated in the SAME change.

NO hardcoded UI strings in code that reaches templates.

## Scope

**In scope** (must be keyed):

- Visible UI text in templates (buttons, headings, drawer sections)
- `aria-label` on interactive controls
- Toast / alert copy
- Modal / dialog copy (title, body, buttons)
- Validation messages shown to user
- Empty-state copy, placeholders
- Kinh catalog metadata (title, description) — keyed under `kinh.<slug>.*`

**Out of scope** (hardcode OK):

- `console.*` log messages
- Internal error identifiers / stack traces
- Internal symbol names, storage keys (`kinh:settings`)
- Author names (proper nouns) — kept as-is in catalog
- Kinh body content in markdown (always Vietnamese, never translated)

## Exception — in-progress dev

During active development of a feature, hardcoded placeholder text is allowed for speed.

MUST migrate to i18n keys BEFORE marking the feature done:

- Spec `## Acceptance` → "all user-facing strings keyed in both `vi.json` and `en.json`" criterion satisfied.
- Task-done signal (`AGENTS.md` §5) is BLOCKED if any hardcoded UI text remains.

## Key naming

Follow nested structure already in `vi.json`:

```
feature.subsection.key
```

Rules:

1. Group by feature top-level key: `site`, `home`, `settings`, `reader`, `kinh`.
2. Sub-group by region/purpose: `theme`, `fontFamily`, `tts`.
3. camelCase leaf keys.
4. Keep `vi.json` and `en.json` key trees structurally identical (same paths, same nesting).
5. For kinh metadata: `kinh.<slug>.title` and `kinh.<slug>.description` for every catalog entry.

## Workflow

1. Identify all user-facing strings in the change.
2. Pick keys following naming rules. Reuse existing keys if applicable.
3. Add keys to `vi.json` AND `en.json` (mandatory, structurally identical).
4. Replace strings in code:
   - Template: `{{ t('key') }}` or `:aria-label="t('key')"`
   - Script (setup): `const { t } = useI18n()` then `t('key')`
5. Pre-task-done check: grep edited files for string literals in templates / `aria-label` → none left.

## Locale switching

`Settings.locale` is the source of truth. `i18n.ts` `setupI18n()`:

1. First boot: locale = `''` → set to `navigator.language.startsWith('vi') ? 'vi' : 'en'`.
2. Watches `settings.locale` → updates `i18n.global.locale.value`.

User changes locale in Settings drawer → drawer writes `settings.locale` → watcher updates i18n → templates re-render.

## Adding a third locale (future)

If adding e.g. `ja.json`:

1. Create `locales/ja.json` mirroring `vi.json` structure (every key present).
2. Add to `messages` import in `.vitepress/theme/i18n.ts`.
3. Add to `Locale` union type in `useSettings.ts` (`'vi' | 'en' | 'ja' | ''`).
4. Add button in `SettingsDrawer.vue` `locales[]` array.
5. Add detection branch in `detectDefault()` in `i18n.ts` if smart-default needed.

Spec required for new locale (`specs.md`).
